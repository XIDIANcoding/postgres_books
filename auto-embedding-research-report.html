1. 执行摘要

核心变化

Auto Embedding 把“数据写入后由应用/ETL 调模型再写回”转变为数据库或搜索服务托管的派生数据生命周期：变更捕获、分块、批处理、回填、重试、向量存储、索引维护、查询侧向量化和模型版本治理。

主流路线

产业界分为四类：数据库扩展内任务系统、字段/索引级托管 Embedding、CDC/湖仓同步向量索引、以及触发器 + 队列 + 外部推理服务的可组合方案。

竞争焦点

真正的差异不在“能否生成向量”，而在新旧数据一致性、回填速度、模型版本治理、筛选向量检索、混合检索、成本与延迟可控性。

关键结论

  • 腾讯云方案工程化程度较高：它不是单纯暴露 get_embedding()，而是引入增量任务、存量任务、pgmq 队列、bgworker、状态视图、错误表、指数退避和 DDL 保护，已经具备数据库内“嵌入任务系统”的雏形。
  • Google AlloyDB、MongoDB、Elastic、Snowflake 更接近产品化 Auto Embedding：它们把源字段、模型、索引或查询侧向量化封装为声明式字段/服务；用户更少感知队列与触发器。
  • pgai Vectorizer 是社区 PostgreSQL 的重要参照：它用 ai.create_vectorizer 声明 loading、chunking、formatting、embedding、destination，内部通过触发器、队列表和外部 worker 保持向量同步，证明社区 PG 不必等待内核原生支持也能实现 Auto Embedding。
  • Aurora/Supabase 代表可组合模式：用 PostgreSQL 触发器、pgmq/pg_cron、Lambda/Edge Function、Bedrock/OpenAI 组合实现，灵活但需要自管可靠性。
  • 学术热点已从“纯向量 ANN”转向“生产级混合查询”：ACORN/RACORN、VBase、FreshDiskANN、MRL 等研究分别解决过滤谓词、关系算子融合、实时更新和多维度自适应检索问题。
  • 社区 PG18 推荐方案：采用“声明式 vectorizer 元数据 + 触发器轻量入队 + pgmq/队列表 + 外部 worker 池 + pgvector 0.8 HNSW/IVFFlat + 查询侧 embed API + 蓝绿模型重嵌入”的架构，优先保证写入路径安全、最终一致和可观测。

2. 技术定义与边界

本报告中的 Auto Embedding 指：当数据库中的文本、图片、音频、视频或复合字段发生新增、更新、删除、回填或查询请求时，系统自动完成向量生成、存储、索引与检索链路维护的能力。 它的边界大于“数据库内置一个 Embedding 函数”，也大于“向量数据库支持 ANN 索引”。

1. 源数据声明
字段、视图、分块规则、元数据过滤字段
2. 变更捕获
触发器、CDC、Delta CDF、索引刷新、对象存储事件
3. 任务调度
队列、批处理、限流、重试、优先级
4. 模型推理
内置模型、外部 API、ONNX Runtime、GPU/CPU 池
5. 写回与索引
vector 列、内部集合、HNSW/IVF/DiskANN/ScaNN
6. 查询闭环
查询向量化、过滤、混合检索、rerank、评测
判断一个方案是否“自动化”的关键：是否能声明源字段与模型后，自动处理历史数据、增量变更、失败重试、索引维护、查询侧文本向量化和观测告警。只提供 embedding(text) 函数通常只能算“半自动”。

3. 腾讯云 PostgreSQL Auto Embedding 技术实现拆解

腾讯云文档《云数据库 PostgreSQL 自动向量化》说明，tencentdb_ai 1.5 新增自动向量化能力，面向 PostgreSQL 17/18， 依赖 pgvector、pgmq 和 tencentdb_ai 后台工作进程。 用户通过一行 SQL 注册任务，后续 INSERT/UPDATE 会触发向量生成并写回目标列。

3.1 核心架构

增量任务

通过 add_incr_autoembedding_task() 创建，系统自动添加 vector 目标列、建立 INSERT AFTER 与 UPDATE BEFORE 触发器，把变更写入队列。

trigger index-time

存量任务

通过 add_backfill_autoembedding_task() 创建，按主键游标批量扫描历史数据并入队，适合先开启增量再回填旧数据。

backfill cursor scan

后台工作进程

通过 shared_preload_libraries='tencentdb_ai' 启动 bgworker，轮询 pgmq，批量调用模型并写回向量列。

queue bgworker

3.2 关键 API 与配置

版本要求PostgreSQL 17/18；腾讯云内核版本 v17.10_r1.19、v18.4_r1.10 及以上；tencentdb_ai >= 1.5。
扩展依赖CREATE EXTENSION tencentdb_ai CASCADE 会安装/依赖 pgvector 与 pgmq；模型需注册到 model_list 并设置 embedding_dim。
增量函数tencentdb_ai.add_incr_autoembedding_task(schema, table, source_columns, model, target_column, index_method, options)，支持 none、hnsw、ivfflat。
存量函数add_backfill_autoembedding_task() 与 run_backfill_autoembedding_task()，目标向量列必须已存在，配置需与增量任务一致。
观测接口autoembedding_status 展示 pending、failed_count、backfilled_rows、last_error；autoembedding_error 记录 row_id、错误码与详情。
关键 GUCautoembedding_batch_size、max_retry、retry_base_ms、max_input_bytes、naptime_ms、autoembedding_database。

3.3 数据处理语义

增量写入：
用户 INSERT/UPDATE
  -> 触发器只入队 row_id / 任务信息
  -> bgworker 批量读取队列
  -> 消费时重新读取源表当前内容
  -> 调用 get_embedding()
  -> 校验维度，并在写回前再次确认源内容未变
  -> 写入 vector 列 / 维护 HNSW 或 IVFFlat 索引

历史回填：
创建 backfill task
  -> 按单列主键游标分批扫描
  -> 批量入队
  -> 与增量消息共用消费、重试、错误记录机制
  -> 推进游标直到 done

3.4 设计亮点

  • 异步化避免阻塞在线事务：触发器不直接调用远程模型，而是入队，由 bgworker 批量消费；这比同步触发器更适合生产写入路径。
  • 消费时重新读取 + 写回前确认：队列不保存完整源文本，避免旧消息覆盖新内容；在模型调用期间如源数据再次变化，会跳过过期写回。
  • 幂等与去重：按行级 row_id 去重，同一行多次变更最终基于最新内容生成向量，符合“最终一致”的语义。
  • 回填与增量可组合：先创建增量任务再创建存量任务，可以减少历史回填期间新增数据遗漏。
  • 运维可观测：任务状态视图、错误表、指数退避、最大重试次数、队列积压等是从 demo 到生产的关键差异。
  • 数据库安全边界：内部函数使用 SECURITY DEFINER，并通过事件触发器阻止活跃任务表的 DROP TABLE/DROP COLUMN。

3.5 局限与风险

一致性是最终一致，不是强一致。 写入事务提交后向量才由后台生成。检索业务需识别向量缺失或滞后状态，例如用 embedding_updated_at、source_hash 或状态列辅助判断。
依赖单列主键。 文档明确要求增量任务表必须有单列主键；复合主键、无主键日志表、分区表等场景需要额外验证。
模型版本治理未完全抽象。 文档关注 embedding_dim，但生产还需要 embedding model version、prompt/schema version、重嵌入策略和新旧索引并行切换。
外部模型服务成为瓶颈。 batch_size、max_input_bytes、naptime_ms 要与模型 QPS、token 限制、费用和失败率一起调优，否则会造成队列积压和检索新鲜度下降。

3.6 与其他方案的定位

腾讯云方案比 Aurora 的“参考架构式自动化”更产品化，因为队列、后台进程、状态视图、错误表被封装进扩展；但相较 Google AlloyDB、MongoDB Atlas、Elastic semantic_text， 它仍要求用户理解 PostgreSQL 扩展、GUC、任务函数与索引方法，属于“数据库内核扩展级自动化”，不是完全托管的字段级体验。

4. 技术机制分层拆解

深入看 Auto Embedding，所有产品都在解决同一个派生数据维护问题：源数据是事实表，embedding 是可重算但昂贵的派生列/派生索引。 因此，评价一个方案不能只看“是否自动调用模型”，而要看它如何捕获变化、如何调度失败重试、如何避免过期写回、如何在过滤检索下保持召回，以及如何处理模型版本升级。

4.1 六层实现模型

层次 关键问题 常见实现 代表方案 工程判断
声明层 用户如何描述“哪些数据要向量化、用什么模型、存到哪里”。 SQL 函数、字段类型、索引定义、服务定义、SDK pipeline。 Tencent add_*_autoembedding_task、pgai create_vectorizer、Elastic semantic_text、MongoDB autoEmbed。 声明越接近 DDL，越容易纳入迁移、审计和权限；SDK pipeline 灵活但治理弱。

4.2 关键技术取舍

触发器 vs CDC

触发器适合源表和向量列同库、需要秒级新鲜度的 OLTP 场景。它的正确做法是只写轻量任务，不在事务里调用模型。CDC适合湖仓、跨库或大规模同步，优点是对业务写路径侵入小，缺点是链路更长、错误定位更复杂。

源表向量列 vs 独立 chunk 表

商品标题、短描述等一行一向量适合源表列；知识库/RAG 文档通常需要一行多 chunk，独立表可记录 chunk 序号、offset、source_hash、ACL、模型版本，避免把文档分块塞回业务主表。

外部 worker vs 数据库 bgworker

bgworker 生命周期由 postmaster 管理，便于封装成扩展，但 C 语言实现、HTTP/凭证处理和崩溃隔离更难。外部 worker（pgai/Supabase/Aurora Lambda）更容易横向扩容和隔离模型依赖，但需要部署与运维。

HNSW/IVFFlat vs DiskANN/ScaNN

社区 pgvector 的 HNSW 是 PG 内最成熟路径，0.8 后通过 iterative scan 缓解过滤后结果不足。DiskANN/ScaNN 更适合超大规模和磁盘友好索引，但社区 PG 主线里可用性、扩展成熟度和运维复杂度需单独评估。

4.5 代表方案详细拆解

下列六类方案与腾讯 Auto Embedding 解决的是同一类问题，但系统边界不同：有的把模型调用放在数据库事务内，有的把任务交给云函数/队列，有的把向量化嵌进搜索索引或同步管道。 因此不能只比较“是否自动”，而要比较写入路径是否阻塞、谁负责重试、向量存在哪里、查询侧是否自动向量化，以及模型/索引版本如何治理。

Aurora aws_ml：数据库内同步调用 Bedrock

定位：这是 Aurora PostgreSQL 的 Aurora Machine Learning 路线，通过 aws_ml 扩展暴露 aws_bedrock.invoke_model_get_embeddings 等 SQL 函数，让数据库函数直接调用 Amazon Bedrock 生成 embedding。

核心组件

  • pgvector：负责 vector 列和 HNSW/IVFFlat 检索。
  • aws_ml / aws_bedrock schema：提供 invoke_model 与 invoke_model_get_embeddings。
  • IAM role：Aurora 集群需要具备访问 Bedrock 的权限。
  • 触发器或存储过程：捕获 INSERT/UPDATE 或批量扫描 NULL embedding 行。

数据流程

INSERT/UPDATE documents
  -> trigger / stored procedure
  -> aws_bedrock.invoke_model_get_embeddings(
       model_id, content_type, json_key, model_input)
  -> 返回 float8[] / 转 vector
  -> UPDATE documents.embedding
  -> pgvector 查询

一致性与失败语义

如果在触发器中同步调用，向量可以接近事务内一致；但 Bedrock 单次调用可能达到百毫秒级，模型超时、限流或 IAM 错误会直接影响写事务。AWS 博客也建议批量过程要分批提交，避免单个长事务阻塞。

优势与风险

  • 优势：SQL 内完成闭环，架构最简单；适合低频写入、后台批量补齐、管理脚本。
  • 风险：把外部模型 SLA 引入数据库事务；高 QPS 写入场景不建议用同步触发器。
  • 与腾讯差异：腾讯 Auto Embedding 把模型调用放到 bgworker 异步执行；Aurora aws_ml 模式更像“数据库内模型调用原语”，任务系统需要用户自己搭。

Aurora SQS/Lambda：云原生异步队列 + 批处理

定位：这是 AWS 官方样例中更适合生产高吞吐的模式。数据库触发器不直接调 Bedrock，而是发布轻量事件；SQS/Lambda 负责削峰、批量、重试和横向扩容。

核心组件

  • Aurora PostgreSQL + pgvector：存源数据和向量。
  • 触发器 / 事件表 / aws_lambda 扩展：把 row id、操作类型、版本信息发布到异步链路。
  • Amazon SQS：提供持久队列、visibility timeout、重试和 dead-letter queue。
  • Lambda worker：批量读取源行、调用 Bedrock embedding、写回 Aurora。
  • RDS Proxy：缓解 Lambda 并发连接数据库的问题。

数据流程

INSERT/UPDATE
  -> DB trigger marks row pending / emits event
  -> async Lambda or SQS message
  -> Lambda batch reads N row ids
  -> fetch latest text from Aurora
  -> call Bedrock embedding in batch
  -> update embedding/status/source_hash
  -> delete SQS message or let it retry

一致性与失败语义

这是最终一致模型。SQS 保证消息在 visibility timeout 后可重试，Lambda 失败可进入 DLQ。若 worker 写回前不校验 source_hash，仍可能把旧文本向量写回；因此生产实现应学习腾讯的“消费时重读 + 写回前比对”。

优势与风险

  • 优势：扩展性和隔离性好；Bedrock 限流、网络失败不会直接拖垮数据库事务；SQS/Lambda 生态成熟。
  • 风险：组件多，VPC、IAM、RDS Proxy、DLQ、幂等写回都要用户设计；跨组件排障比数据库内 bgworker 复杂。
  • 与腾讯差异：腾讯把队列和 worker 封装到数据库扩展；AWS 模式把队列和 worker 外置到云服务，弹性更强但工程拼装更多。

Supabase Automatic Embeddings：pgmq + pg_cron + pg_net + Edge Function

定位：Supabase 的方案是社区 Postgres 组合式路线，核心是把 embedding 生成做成数据库内可观察的异步队列任务，实际模型调用由 Edge Function 完成。

核心组件

  • pgvector：存储和查询 embedding。
  • 触发器：INSERT/UPDATE 时把 embedding job 写入 pgmq；部分实现会先把 embedding 置空或标记 pending。
  • pgmq：队列、visibility timeout、read/delete/archive。
  • pg_cron：周期性运行队列处理 SQL，例如每 10 秒批量读消息。
  • pg_net：从数据库异步 HTTP 调 Supabase Edge Function。
  • Edge Function：调用 OpenAI 或其他 provider，回写数据库并删除队列消息。

数据流程

INSERT/UPDATE source row
  -> trigger queues job in pgmq
  -> pg_cron calls process_embedding_jobs()
  -> process function batches messages
  -> pg_net.http_post(Edge Function)
  -> Edge Function calls embedding provider
  -> UPDATE source.embedding
  -> pgmq.delete(message) on success
  -> failure: message visible again after VT

一致性与失败语义

Supabase 文档明确这是异步 pipeline：刚插入或更新后，embedding 可能暂时为空或旧值，稍后由 Edge Function 补齐。失败后消息留在队列里，visibility timeout 到期后由下一次 cron 继续处理。

优势与风险

  • 优势：全部由开源/托管 Postgres 扩展组合而成，便于迁移到社区 PG；队列可查、可重试、可归档。
  • 风险：pg_cron 轮询粒度影响实时性；Edge Function 并发和 provider key 管理要单独做；默认样例更偏参考实现，不等于完整产品能力。
  • 与腾讯差异：两者都使用 pgmq 思路；腾讯用数据库 bgworker 常驻消费，Supabase 用 pg_cron + HTTP Edge Function 外置消费。

MongoDB autoEmbed：索引级托管 embedding

定位：MongoDB Atlas Automated Embedding 把向量化嵌入 Vector Search 索引生命周期。用户定义 autoEmbed 字段后，Atlas 在索引构建、文档插入/更新和查询时自动调用 Voyage AI 模型。

核心组件

  • autoEmbed index field：声明原始文本字段、模型、相似度和过滤字段。
  • Voyage AI 模型服务：Atlas 托管和管理 embedding 模型。
  • 内部生成向量集合：生成的 embedding 异步存储在同集群的 __mdb_internal_search 内部数据库/集合。
  • $vectorSearch query.text：查询时可直接传文本，MongoDB 生成 query embedding 后检索。

数据流程

Create Vector Search index with autoEmbed
  -> initial sync scans indexed text field
  -> Atlas sends text to Voyage AI
  -> embeddings stored in __mdb_internal_search
  -> insert/update indexed field triggers async re-embedding
  -> $vectorSearch { query: { text: "..." } }
  -> query text embedded with same/compatible model
  -> vector search returns ranked documents

一致性与失败语义

这是索引最终一致：文档写入后要等待索引构建/更新完成才可被语义检索到。MongoDB 文档强调 index-time 和 query-time 使用同一或兼容模型；模型不兼容会导致向量空间错配。Atlas 还对首次构建、增量更新和查询分别做速率隔离。

优势与风险

  • 优势：开发者不需要管理向量列、worker、队列和 query embedding；字段级体验最接近“开箱即用”。
  • 风险：模型选择和内部存储受 Atlas 托管能力限制；成本按 index/query token 计；复杂重嵌入和跨平台迁移可控性弱于自建 PG。
  • 与腾讯差异：腾讯暴露数据库任务和 vector 列，用户可 SQL 观测；MongoDB 把 embedding 作为搜索索引内部资产，用户更少接触底层实现。

PolarSearch AutoETL：PolarDB 变更同步 + 搜索侧 ingestion pipeline

定位：PolarSearch 是 PolarDB 的分布式搜索/分析引擎，兼容 Elasticsearch/OpenSearch 生态。AutoETL 负责把 PolarDB 表变化同步到 PolarSearch；向量化发生在 PolarSearch ingestion pipeline 中。

核心组件

  • PolarDB 源表：业务数据仍写在 PolarDB。
  • AutoETL 同步任务：通过如 dbms_etl.sync_by_map 创建表到索引的映射，捕获 insert/update/delete。
  • PolarSearch index：保存原始字段、向量字段、全文字段和标量过滤字段。
  • ingestion pipeline / text_embedding processor：写入索引前读取指定文本字段，调用外部 embedding 模型并写入 knn_vector 字段。
  • search pipeline / rerank processor：查询阶段可先 neural/vector 检索，再 rerank，最后进入 RAG 生成。

数据流程

PolarDB table insert/update/delete
  -> AutoETL captures changes
  -> stream document to PolarSearch index
  -> default ingestion pipeline intercepts document
  -> text_embedding processor calls external embedding model
  -> write raw text + vector field into index
  -> query pipeline: neural retrieval -> rerank -> RAG

一致性与失败语义

这是跨系统近实时一致。源库提交后，搜索索引和向量字段通过 AutoETL 异步追赶。优点是不会污染 OLTP 写路径；风险是同步延迟、pipeline 失败、模型限流会让搜索索引滞后。删除操作也必须正确映射到 PolarSearch，否则会出现搜索侧残留。

优势与风险

  • 优势：适合全文 + 向量 + 标量混合检索，搜索节点可独立扩展；ingestion/search pipeline 能自然加入 embedding 和 rerank。
  • 风险：不是源数据库内强一致；调试要跨 PolarDB、AutoETL、模型服务和 PolarSearch 多个系统；对 PG 原生 SQL 使用者心智更高。
  • 与腾讯差异：腾讯在同一个 PostgreSQL 实例内写回 vector 列；PolarSearch 把向量资产同步到搜索引擎，更像“数据库 + 搜索平台”的架构。

PolarDB polar_ai：数据库内 embedding 函数/生成列

定位：PolarDB for PostgreSQL 的 polar_ai 路线更接近“数据库内函数 + pgvector”。用户通过 polar_ai.ai_text_embedding() 将文本转换为向量，并可把它定义为 STORED generated column，再用 HNSW/IVFFlat 索引。

核心组件

  • polar_ai：提供文本转向量函数，可连接内置或自定义模型能力。
  • pgvector / VECTOR 类型：存储 embedding，支持距离算子。
  • STORED generated column：在写入/更新时根据文本表达式生成向量。
  • HNSW / IVFFlat：对 generated vector column 建 ANN 索引。

数据流程

ALTER TABLE items
  ADD COLUMN embedding_vec vector(1536)
  GENERATED ALWAYS AS (
    polar_ai.ai_text_embedding(description)
  ) STORED;

INSERT/UPDATE description
  -> generated column expression executes
  -> embedding_vec materialized
  -> HNSW/IVFFlat index maintained
  -> query uses ORDER BY embedding_vec <-> polar_ai.ai_text_embedding(query)

一致性与失败语义

STORED generated column 语义上接近同步：源字段变化时向量列随写入计算并物化，查询立即能看到匹配的向量。但这也意味着模型调用延迟和失败会进入写事务；如果 embedding 函数调用远程模型，高频写入风险类似 Aurora aws_ml 同步模式。

优势与风险

  • 优势：DDL 简洁，和 pgvector 查询天然结合；适合短文本、低频写入、需要写后立即检索的场景。
  • 风险：不适合长文档一对多 chunk；模型调用失败可能导致业务写入失败；模型版本升级需要重写 generated column 或新列/新索引。
  • 与腾讯差异：腾讯选择异步任务系统降低写路径风险；polar_ai generated column 选择同步物化换取语义简单。

4.6 一致性语义

  • 强一致：同步事务内生成向量；代价是写入延迟、失败传播和模型服务耦合。
  • 读己之写但向量延迟：主数据可立即读到，向量字段异步补齐；大多数 Auto Embedding 产品采用此模式。
  • 近实时索引：Snowflake/Databricks/PolarSearch 这类服务通常按刷新或同步管道维护索引，适合搜索和分析，不适合严格事务语义。

4.7 生产系统必须补齐的元数据

recommended columns:
  source_hash          -- 源字段归一化后的 hash，用于判断过期写回
  embedding_model      -- 模型名称，如 hunyuan-embedding / gemini-embedding-001
  embedding_version    -- 模型版本或端点版本
  embedding_dim        -- 向量维度
  embedding_status     -- pending / ready / failed / stale
  embedding_updated_at -- 最近成功生成时间
  embedding_error      -- 最近错误摘要
  chunk_id / parent_id -- 文档分块场景的父子关系
  acl / tenant_id      -- 过滤检索必须下推的安全字段

autoEmbed 索引在字段级声明模型，MongoDB 在 index-time 自动生成并异步持久化 embedding，同时在 $vectorSearch 查询中接受文本 query 并自动生成查询向量。

semantic_text 字段自动完成 chunking、inference、向量存储，并支持 match、knn、sparse_vector 查询。Elastic 建议生产环境显式指定 inference_id，避免默认端点变化造成多索引模型不一致。

启示：搜索引擎类产品在字段映射、混合检索和 rerank 体验上领先。

Aurora：多种自动化模式的参考实现

AWS 官方博客总结了从同步触发器调用 Bedrock，到 Lambda、SQS、pg_cron 批处理的多种架构。它强调 100-400ms 级单次 embedding 调用不适合长事务，应通过批处理或异步队列降低写入路径风险。

启示：Aurora 当前更像提供积木，自动化程度取决于团队工程能力。

阿里云：PG 内向量能力 + 搜索节点 AutoETL

PolarDB for PostgreSQL 支持优化版 pgvector 和 polar_ai 嵌入函数；PolarSearch 则面向更大规模混合搜索，公开资料提到 AutoETL、自动 embedding 与 reranking 管道。

启示：一体化数据库和外挂搜索节点会并存：前者低改造，后者面向十亿/百亿级和搜索生态。

腾讯云：把 Auto Embedding 做成 PostgreSQL 扩展任务系统

腾讯方案直接在数据库内封装任务、触发器、pgmq、bgworker 与错误表，用户只需注册任务；这比外部 ETL 更接近数据库原生，同时保留 SQL 可观测和 pgvector 生态。

启示：适合已经在 TencentDB for PostgreSQL 上构建 RAG/语义检索的业务。

pgai Vectorizer：社区 PG 的声明式向量化 pipeline

pgai 的价值不只是自动调用 OpenAI/Ollama，而是把加载、分块、格式化、嵌入模型和目标表/列抽象为 SQL 配置；worker 轮询队列并批量处理，向量作为最终一致的派生数据维护。

启示：社区 PG18 方案应复用这种 DSL，但需要补齐指数退避、死信、优先级、模型蓝绿切换和 query-time embedding。

6. 学术层面的最新方案与趋势

学术界并不常把问题命名为 Auto Embedding，但其关键技术分散在向量数据库、混合检索、动态 ANN、表示学习、数据库查询优化和 RAG 系统中。 与产业落地最相关的方向如下。

ACORN / ACORN-1：谓词感知的 HNSW 过滤检索

ACORN 提出 predicate subgraph traversal，使 HNSW 在带结构化过滤条件时不再简单前过滤或后过滤。论文宣称在固定 recall 下相对既有方案有 2-1000 倍吞吐提升。ACORN-1 进一步降低构建成本，Lucene/Elastic 已公开介绍类似 ACORN-1 的 filtered HNSW 优化。

Matryoshka Representation Learning：可变维度 Embedding

MRL 训练单个模型在不同前缀维度上都保持可用语义表示，可用低维前缀做粗召回，再用全维向量 rerank。它为 Auto Embedding 带来“按成本/延迟动态选择维度”的能力。

hybrid retrieval RAG systems

6.1 对 Auto Embedding 产品的影响

  • 从“生成向量”升级为“生成可治理的检索资产”：模型版本、分块版本、维度版本和评测集会成为数据库元数据。
  • 过滤检索会成为核心卖点：企业 RAG 几乎总带 tenant、ACL、时间、品类、地域过滤；ACORN/VBase 类研究会进入主流数据库优化器。
  • 索引新鲜度是下一个战场：FreshDiskANN/SPFresh/LSM-VEC 的思路会影响云数据库如何在大规模动态数据上避免频繁重建 HNSW/IVF。
  • 自适应成本控制会产品化：MRL、量化、低维粗召回、全维 rerank、查询复杂度路由，会成为 Auto Embedding 的成本优化层。
  • 查询侧模型一致性需要制度化：index-time 和 query-time 的模型必须兼容，否则同一字段的向量空间不一致会直接损害召回。

7. 基于社区 PostgreSQL 18 的 Auto Embedding 方案设计

目标是在不依赖云厂商闭源能力的前提下，基于社区 PostgreSQL 18、pgvector 0.8+、pgmq（或等价队列表）、外部 worker 和可选 pgai 能力，设计一个可落地的 Auto Embedding 系统。 该方案刻意不把模型 HTTP 调用放进业务事务，也不要求修改 PostgreSQL 内核；它把 embedding 看成类似全文索引/物化视图的派生资产，通过元数据、队列和 worker 保持最终一致。

7.1 设计目标与非目标

目标

  • 一条 SQL 声明源表、源字段、分块、模型、目标表/列和索引策略。
  • 自动处理历史回填、增量 INSERT/UPDATE/DELETE、失败重试和可观测状态。
  • 支持短字段一对一向量列和长文档一对多 chunk 表两种目的地。
  • 支持查询侧文本自动向量化，并强制使用与索引兼容的模型版本。
  • 支持模型升级的蓝绿重嵌入，不破坏线上检索。

非目标

  • 不追求在源事务内强一致生成向量；默认采用最终一致。
  • 不把复杂模型依赖、HTTP 客户端和密钥处理放入数据库后端进程。
  • 不替代专业向量数据库在百亿级、复杂 filtered ANN 上的所有能力。
  • 不把 chunking、rerank、评测逻辑硬编码在业务表触发器里。

7.2 PG18 能力如何被利用

PG18 / 社区组件 在方案中的作用 设计细节
PostgreSQL 18 AIO 提升大表回填扫描、VACUUM 和 bitmap/seq scan 的 I/O 效率。 回填 worker 按主键范围扫描历史数据；PG18 的异步 I/O 对顺序扫描和 vacuum 更友好，可降低大规模 backfill 对存储的阻塞。
UUIDv7 作为任务、chunk、embedding 版本的时间有序 ID。 比 UUIDv4 更利于 B-tree locality；任务表和错误表使用 uuidv7() 便于按时间排查。
Skip scan / B-tree 提高多租户 metadata filter 的普通索引利用率。 为 (tenant_id, acl_hash, updated_at)、(vectorizer_id, status, next_run_at) 等建立复合索引；PG18 skip scan 增加部分条件下的可用性。
Generated columns 生成规范化文本、source_hash 或过滤字段。 hash/status 等用于写回一致性的字段建议 STORED；纯展示或轻量拼接可用默认 virtual generated column。
pgvector 0.8+ 存储与检索向量，支持 HNSW/IVFFlat、halfvec、sparsevec、iterative scan。 过滤检索默认启用 hnsw.iterative_scan='relaxed_order'，并结合 B-tree 过滤索引；大维度可评估 halfvec。
pgmq / 队列表 承载任务消息、visibility timeout、重试和归档。 若不用 pgmq，可用普通表 + FOR UPDATE SKIP LOCKED 实现；pgmq 提供更接近 SQS 的 read/delete/archive 语义。
LISTEN/NOTIFY 降低 worker 纯轮询延迟。 触发器入队后发 NOTIFY，worker 被唤醒；NOTIFY 只做提示，可靠性仍由队列表保证。

7.3 总体架构

业务写入
  -> AFTER INSERT/UPDATE/DELETE 触发器只写轻量 job(row_pk, source_hash, op, vectorizer_id)
  -> pgmq / ae_job_queue 持久化任务，并 NOTIFY worker
  -> worker 池按 vectorizer_id + 优先级读取任务，批量回源表读取最新内容
  -> chunking / formatting / provider batching / rate limiting
  -> 调 embedding provider 或私有模型服务
  -> 在同一事务中校验 source_hash，upsert embedding 表或源表 vector 列
  -> 标记 job done；失败则按指数退避设置 next_run_at，超过阈值进 dead-letter
  -> 查询 API 使用同一 model_version 生成 query embedding，走 pgvector + metadata filter + optional rerank

SELECT autoembed.create_vectorizer(

  source_table       => 'public.kb_article'::regclass,
  primary_key        => ARRAY['id'],
  source_columns     => ARRAY['title', 'content'],
  destination        => autoembed.destination_table('public.kb_article_embedding'),
  chunking           => autoembed.chunking_recursive(chunk_size => 800, overlap => 120),

                         endpoint_secret => 'embedding_endpoint',
                         model => 'bge-m3',
                         version => '2026-07-01',

  indexing           => autoembed.indexing_hnsw(metric => 'cosine', m => 16, ef_construction => 128),

  query_embedding    => true
);
为什么不直接复用源表 generated column 调模型？ PG18 virtual generated column 是读时计算，不适合触发外部模型调用；stored generated column 是写时计算，会把模型延迟放进事务。正确做法是 generated column 只生成轻量、确定性的 source_hash 或文本规范化结果，模型调用交给异步 worker。

7.6 worker 处理语义

  1. 取任务：按 next_run_at、priority、vectorizer_id 拉取，使用 pgmq visibility timeout 或 FOR UPDATE SKIP LOCKED，避免多 worker 重复处理。
  2. 回源读取：队列只存主键和 source_hash，worker 处理前重新读取当前源行，防止旧消息携带旧文本。
  3. 去重合并：同一行多次 update 合并为一条最新任务；delete 任务优先删除对应 embedding。
  4. 分块和格式化：chunking 应确定性，chunk_no 和 source_hash 共同决定幂等写入。
  5. 批量推理：按 provider 限制合并 batch，记录 token、latency、provider request id。
  6. 写回校验：写回前再次比较当前 source_hash；若变化，放弃本次结果并重新入队。
  7. 失败处理：区分可重试错误（429/5xx/timeout）和不可重试错误（维度不匹配、文本过长、权限错误），使用指数退避和 dead-letter。
-- 伪代码：worker 领取任务
WITH picked AS (
  SELECT job_id
  FROM autoembed.embedding_job
  WHERE next_run_at <= now()
  ORDER BY priority, created_at
  LIMIT 100
  FOR UPDATE SKIP LOCKED
)
UPDATE autoembed.embedding_job j
SET locked_at = now(), locked_by = $worker_id
FROM picked
WHERE j.job_id = picked.job_id
RETURNING j.*;

7.7 查询 API 与过滤检索策略

CREATE OR REPLACE FUNCTION autoembed.search(
  vectorizer_name text,
  query_text text,
  tenant bigint,
  acl text,
  k int DEFAULT 10
) RETURNS TABLE(source_pk jsonb, chunk_text text, score float8)
LANGUAGE sql
AS $$
  -- 实际实现中 query embedding 可由 SECURITY DEFINER 函数调用 worker-side cache/provider
  WITH q AS (
    SELECT autoembed.embed_query(vectorizer_name, query_text) AS v
  )
  SELECT e.source_pk,
         e.chunk_text,
         1 - (e.embedding <=> (SELECT v FROM q)) AS score
  FROM kb_article_embedding e
  WHERE e.tenant_id = tenant
    AND e.acl_hash = acl
    AND e.embedding_model_version = autoembed.active_model_version(vectorizer_name)
  ORDER BY e.embedding <=> (SELECT v FROM q)
  LIMIT k;
$$;

对 pgvector 0.8+，过滤查询建议在会话或函数内设置： SET LOCAL hnsw.iterative_scan = 'relaxed_order'， 并结合 hnsw.max_scan_tuples、hnsw.ef_search 做离线 recall/latency sweep。 如果过滤条件极端选择性（例如 tenant + ACL 后只剩万分之一数据），单纯 HNSW 后过滤仍可能不稳定，此时应考虑分区、分租户索引、预过滤候选集 rerank，或接入 ACORN/DiskANN 类系统。

7.9 安全与运维

  • 密钥：数据库只保存 secret 引用，worker 从 Vault/KMS 取真实密钥；避免把 provider key 存在普通表。
  • 权限：DDL/API 用 SECURITY DEFINER 收敛权限；用户只能操作自己拥有的 source table。
  • PII：在 formatting 阶段支持脱敏函数；记录哪些字段被发送到外部模型。
  • 观测：提供 autoembed.vectorizer_status 视图：pending、running、failed、dead_letter、oldest_job_age、tokens/min、avg_latency、last_error。
  • 容量：回填与增量分队列/优先级，增量队列优先；回填 batch 根据 provider QPS 和数据库 I/O 自动限流。
  • 清理：DELETE 源行触发删除 embedding；模型版本下线后清理旧 embedding 和旧 HNSW 索引。

8. 工程评估框架

功能维度

  • 是否支持历史回填与增量自动同步。
  • 是否支持查询文本自动向量化。
  • 是否支持多字段组合、视图、分块、metadata filter。
  • 是否支持模型/维度/索引版本变更后的重嵌入。
  • 是否有状态、错误、重试、限流和告警。

性能维度

  • 写入事务额外开销与 P99 延迟。
  • 回填吞吐、模型 QPS、token 成本、失败重试成本。
  • 队列积压到检索可见的端到端新鲜度。
  • ANN recall@k、nDCG、MRR、过滤查询下的召回稳定性。
  • 索引构建/维护时间、内存、磁盘与量化损失。

治理维度

  • 密钥是否进入数据库，是否可 KMS/角色隔离。
  • 源文本是否出域，是否支持私有模型或内网推理。
  • 是否记录 embedding lineage、模型版本和数据血缘。
  • 删除源数据时向量、内部集合、索引是否同步删除。
  • 租户/ACL 过滤是否在向量检索阶段下推。

质量维度

  • 分块策略：固定窗口、语义切分、结构化标题、重叠比例。
  • 检索策略：dense、sparse、BM25、hybrid、rerank。
  • 更新策略：全量重嵌入、增量变更、模型 A/B、双写索引。
  • 评测：人工标注、线上点击、问答正确性、幻觉率。
  • 漂移监控：源数据分布变化、模型版本变化、召回下降。

9.2 对腾讯云 Auto Embedding 的改进建议

  1. 显式加入模型版本与 source_hash：文档可建议目标表增加 embedding_model_version、source_hash，便于过期向量检测和重嵌入。
  2. 提供查询侧向量化封装：类似 MongoDB/Elastic，支持在检索函数中直接传文本 query，并自动使用任务同款模型生成 query embedding。
  3. 支持任务级限流与优先级：对存量回填和实时增量使用不同队列/优先级，防止回填拖慢新数据新鲜度。
  4. 补充分区表、复合主键和多租户示例：企业表结构复杂，单列主键限制应配套迁移方案。
  5. 支持模型切换的蓝绿重建：自动创建新向量列/新索引、后台回填、双读评测、原子切换，降低模型升级风险。
  6. 引入混合检索模板：结合 pg_textsearch、BM25、pgvector 和 rerank，给出 RAG 质量评测样例。
不建议盲目使用 Auto Embedding 的情况：源表写入极高且对事务延迟极敏感；数据包含不可出域敏感内容但模型服务在外网；embedding 模型频繁切换但没有版本治理；检索强依赖 ACL 过滤但向量索引不支持过滤下推。

9.3 如果基于社区 PG18 自研，建议采用的默认技术栈

组件 默认选择 原因
向量类型与索引 pgvector 0.8+，HNSW；大维度评估 halfvec。 社区成熟度最高，PG 内 SQL 查询体验最好；iterative scan 改善过滤后结果不足。
任务队列 pgmq 或普通队列表 + FOR UPDATE SKIP LOCKED。 避免引入外部 MQ；visibility timeout 和归档语义适合 embedding job。
执行器 外部 worker 池优先，后续再考虑 C bgworker。 更易处理 HTTP、并发、provider SDK、密钥、GPU/CPU 隔离和滚动升级。
声明式 API 参考 pgai 的 loading/chunking/formatting/embedding/destination DSL。 可迁移、可审计、可复用，比把逻辑写散在业务触发器里更稳。
检索质量 dense vector + BM25/全文检索 + RRF + rerank。 多数企业知识库单靠 dense embedding 不够稳定，混合检索是更稳的默认路径。
